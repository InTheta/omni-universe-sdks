# v0.8.1 release and migration notes

This coordinated release contains the TypeScript SDK, matching repository
examples and local MCP adapter. The GitHub release archive becomes installable
only after the final merged revision is tagged and the asset is published.
A merged pull request or green source CI is not proof that the asset exists.
npm registry publication is a separate step.

## Install and runtime migration

**Node >=22.12 is required.** This raises v0.8.0's Node >=20.19 minimum because
of the pinned Hyperliquid execution dependency. Upgrade the runtime before
upgrading the SDK.

Once the tagged asset is available:

```sh
npm install https://github.com/InTheta/omni-universe-sdks/releases/download/v0.8.1/omni-terminal-sdk-0.8.1.tgz
```

Until publication, build the reviewed source revision. From the repository root:

```sh
cd packages/typescript
npm ci
npm run verify
npm run verify:live
```

`verify:live` forces public/free variants. It cannot enable a paid call through
inherited payment flags. Repository npm scripts are not installed as commands
in an external consumer project; the tarball contains runnable example sources
and guides. Import application APIs from `@omni-terminal/sdk`, and broker APIs
from `@omni-terminal/sdk/brokers`.

The repository testnet-agent package uses `file:../../packages/typescript`.
Build the SDK first, then run `npm ci && npm run verify` from
`examples/testnet-agents`. It must use the matching reviewed source revision.
The local MCP trading adapter is a repository example, not a new trading
capability of Omni's deployed seller MCP.

## Data, payments and MCP

- All **13 HTTP products** have SDK/example coverage: ten JSON products,
  including premarket research, and three PNG screenshot products.
- PNG helpers validate a complete PNG signature, IHDR dimensions and byte limits.
  They support bounded request timeouts, including adapters that ignore aborts.
- The deployed MCP supports a free catalog and **five paid research tools**.
  Tool arguments, product contracts and settlement metadata are validated.
  Connection, listing, calls and shutdown have controlled error boundaries.
- Research and recovery examples use public SDK interfaces. Unpaid challenge
  inspection and free health/catalog requests never create a payment.
- EVM payment policy binds the receiver, exact scheme, supported network/asset,
  positive amount and expiry. Per-call and optional aggregate/authorization
  ceilings reserve before signing across calls sharing one instance.
- Paid bundles preflight known charges and preserve hard ceilings. Defaults do
  not silently rise when prices change. Reservations and same-operation replay
  are instance-local, not durable exactly-once settlement guarantees.

Prices come from the live unsigned challenge, not this release number.
A timeout or failed response after signing may represent a settled charge.
Reconcile receipt/audit/chain state before approving another payment. The
October 15 SDK workflows do not claim a newly funded full-route purchase.

## Error compatibility changes

HTTP and contract errors no longer expose arbitrary upstream bodies, status
text or raw metadata. Handle allowlisted `OmniApiError.code`, `status` and
sanitized `requestId`/`retryAfter`; do not parse seller prose or rely on raw
`details`. Unknown remote codes are replaced with a controlled SDK code.

Payment transport failures use `OmniPaymentError` with controlled codes,
`requiresReconciliation: true` and `retryable: false`. MCP wrapper protocol
errors use `OmniMcpProtocolError` and retain only operation and safe numeric
protocol code. Untrusted messages, data and causes are omitted. Abort/timeout
names remain recognizable. Direct use of the raw underlying clients requires
its own error-handling policy.

These changes intentionally narrow error contents for callers that previously
logged or parsed upstream bodies. Historical v0.8.0 behavior is unchanged.

## Guarded testnet execution and accounting

`GuardedTestnetExecutor` fixes Hyperliquid testnet, owning account, exact
validator instrument, local signer authority, bounded notional, quote expiry and
Omni builder policy. Data payment, application authentication, trading
authorization and builder-fee approval remain separate.

Durable journals precede writes. Unknown outcomes require reconciliation of the
same client order ID. Cancellation uses current exact-instrument metadata and
authoritative order scope, so stale/unavailable order books cannot block it.
The legacy agent now rejects intent/config instrument mismatches before market
access. The runner preserves its journal and lock for unindexed fills,
unexplained exposure or incomplete cleanup; success requires flat final exposure.

The local MCP trading agent accepts additive tool discovery while requiring
every core lifecycle tool. Its real MCP transport regression covers both eight
core tools and the ninth read-only accounting tool, plus missing-core rejection.

`recentReconciliation` and the local `recent_reconciliation` tool expose
bounded instrument-period fills, signed fees/funding and observed realized cash
PnL. Decimal strings preserve precision. Builder fees are a subset of total
fees and are not subtracted twice. Unrealized PnL is a separate current snapshot.
Expected order IDs do not filter period-wide totals or assign funding to orders.

Request budgets, explicit time windows, whole-operation deadlines, pagination,
same-millisecond saturation and upstream retention limitations remain visible.
`fullLedgerReconciled` and retention verification stay false; this is not a
complete account-equity ledger.

## Verification and remaining limits

The release process runs contract/unit/recovery checks, package typechecks and
builds, no-spend examples, documentation/public-boundary checks, dependency
audit, and a clean packed-package consumer installation. Live read-only runs
exercise deployed discovery/challenges and local SDK/MCP accounting parity.
Fixtures are labeled deterministic tests; they do not establish venue fills.

Release preparation on 15 October 2026 used Dell Linux and Node 22.23.2:
SDK verification passed 87 tests, typechecks/builds, example demos, 61 relative
documentation links, public-boundary checks, a clean 101-file packed consumer
installation and a zero-vulnerability runtime audit. The matching agent package
passed 13 tests and its runtime audit. Five live read-only SDK tests passed,
including discovery and unpaid challenges for all 13 HTTP products. These are
source/package and free integration results, not evidence of published assets
or funded execution.

A funded guarded order lifecycle and authoritative builder credit remain
unverified. A builder field or fill `builderFee` alone does not identify the
credited builder. Execution requires a dedicated approved testnet signer,
funded testnet account and separately approved disclosed builder fee. No
mainnet trading or additional paid usage is authorized by installing this SDK.

Supported guarded execution excludes amendment/cancel-replace, vault/subaccount
execution, spot, mainnet and arbitrary existing-position closure. Reading a
vault's public state does not grant vault authority. Fee/funding summaries do
not prove complete historical account reconciliation.
